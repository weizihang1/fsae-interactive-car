# 交互式赛车数字模型 方案 v2

> 目标：一个网址打开就是完整赛车——**能转、能拆、能吹风、能开**；同时每个零件都能拿到独立文件，在 Blender 里打开修改。
> 依据：本文件所有选型均已做可达性核查（2026-10-13）。

---

## 0. 你的需求拆成四个可独立验收的子系统

| 你的原话 | 技术形态 | 验收标准 |
| --- | --- | --- |
| 一个整体、可交互的汽车模型 | GitHub Pages + three.js 单页 | 给一个网址，打开即可旋转缩放、点击零件看信息 |
| 每个重要零件可独立拆出来看（Blender 打开） | 装配树 + 逐零件导出 `.blend` / `.glb` / `.stl` | 在 Blender 里打开，每个零件是独立且有名称的对象，可直接编辑 |
| 风洞可视化测试 | 真实 CFD（CI 里跑）+ 浏览器内可视化 | 有速度/偏航角滑杆，能看到流线、表面压力、尾流 |
| 能在场景里跑动测试 | three.js + Rapier 车辆物理 + 赛道场景 | 键盘可驾驶，追随相机，遥测 HUD，悬架行程联动 |

**交付形态一句话**：一个 GitHub 仓库 + 一个网站。仓库是唯一真值来源，网站是它的可交互呈现，Blender 文件是它的可编辑形态。

## 1. 架构：数据 → 生成 → 呈现

```
fsae-car/
├─ params/            零件清单与参数（parts.yaml）：名称 / 系统 / 材料 / 质量 / 装配变换
├─ cad/               团队现有 STEP 装配（若有）
├─ geometry/          参数化建模（CadQuery/build123d）或 STEP 导入转换
├─ blender/           无头脚本：组装、命名、材质、集合树、导出 .blend / GLB、渲染
├─ cfd/               RapidFOAM 配置 + 气动面 STL + 结果后处理 → 流场数据
├─ sim/               车辆动力学参数（质量、轴距、轮胎、动力）
├─ site/              three.js 单页应用：整机 / 拆解 / 风洞 / 驾驶 四模式
├─ .github/workflows/ build.yml（几何+Blender）· cfd.yml（风洞）· pages.yml（发布）
└─ outputs/           产物：.blend .glb .stl .csv 图 视频 报告
```

要点：`params/` 是唯一真值来源。改一个数字 → 提交 → CI 重新生成几何、Blender 文件、网页数据。这样"修改"是可追溯、可回退的，而不是各自为政的一堆文件。

## 3. 四个模式的具体定义

### 3.1 整机模式（静止状态交互）

- 旋转 / 缩放 / 平移，预设视角：正前、正侧、顶视、等轴、俯视
- 点击任意零件 → 高亮 + 信息卡（名称、所属系统、材料、质量、尺寸、对应图纸）
- 图层开关：车架 / 悬架 / 转向 / 制动 / 动力 / 空气动力学套件 / 轮胎轮辋
- 关键尺寸标注：轴距、轮距、离地间隙、重心高度
- 质量表联动：点表格里的行 → 三维里高亮对应零件

### 3.2 拆解模式

- 左侧装配树按系统分组，点节点 → 相机飞向该零件，其余半透明
- 爆炸视图滑杆；单个零件可"抽出来"悬停在侧边
- 逐级拆解动画：整车 → 系统 → 零件
- 每个零件提供独立下载：`.blend`（Blender 直接打开）/ `.glb`（通用）/ `.stl`（打印或进 CFD）

### 3.3 风洞模式（分两级，可信度先说清）

| 级别 | 成本 | 内容 | 定位 |
| --- | --- | --- | --- |
| **L1 交互级** | 秒级，浏览器内 | 预计算速度场驱动粒子平流；流线（色=速度）、表面压力云图（色=压力系数）、尾流涡；速度/偏航角滑杆在预计算档位间插值 | 讲解、直觉、对比 |
| **L2 计算级** | 每次 1–4 小时 CI 机时 | RapidFOAM 生成 OpenFOAM 算例（snappyHexMesh + 边界层 + simpleFoam k-ω SST）→ Cd / Cl / 前后升力分配 / 流线 | 真实数字、趋势对比 |

额外可选：Blender 内置烟雾/流体模拟 → 出一段"风洞烟线"视频，用于报告与答辩（好看，但不是物理准确）。

L2 的真实边界（必须写进报告）：粗网格稳态 RANS + 简化旋转轮，**结论适合看趋势与做方案对比（例如改尾翼前后谁更优），不足以支撑精确气动报表**。RapidFOAM 会一并给出 y+ 报告与网格质量检查，这两项会随结果一起展示。

### 3.4 驾驶模式

- 场景：地面 + 赛道（由中心线 CSV 生成路面与路肩）+ 天空环境
- 车辆：Rapier 射线车辆或简化自行车模型，参数取自 `sim/`
- 操作：方向键 / WASD 控制油门、刹车、转向；追随相机、车内视角、自由视角可切换
- HUD：速度、纵向/横向加速度、方向盘转角、四轮悬架行程动画（与悬架运动学联动）

诚实边界：这是**游戏级物理**，能看动态姿态、悬架压缩回弹、转向响应，**不能替代圈速仿真**。要圈速结论得另接准稳态（QSS）求解器，那是另一个项目。

## 4. 几何从哪来 —— 本项目最大的不确定项

已核查：**GitHub 上没有可直接使用的 FSAE 整车三维模型**。所以几何必须自建或从你们队内拿。三条路：

| 路线 | 前提 | 代价 |
| --- | --- | --- |
| **A 导入现有装配** | 你手上有团队的 STEP / SolidWorks 装配 | 最省力。用 OCP/CadQuery 读 STEP → 按零件拆网格并保留名称 → 生成装配清单。代价：丢失参数化，只能改形不能改参数 |
| **B 从零参数化** | 无现成 CAD | 工作量最大，但每个尺寸都可控、可迭代、可扫描 |
| **C 混合（推荐）** | —— | 车架/悬架用参数化精确建（为后续 FEA 与设计迭代服务），外观件（车身、空套）用简化面片，够看、够吹风、够开 |

风洞环节对几何有硬性要求：气动外表面必须**水密、无自交、单位米、ASCII STL**（RapidFOAM 会跑 `surfaceCheck` 检查，带缺陷会直接报出来）。轮胎需单独提供，旋转轮在 L2 中简化处理。

## 5. 阶段划分与验收

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| **S0** 骨架 | 仓库结构 + 网站壳 + 一套比例正确的占位几何思路 | 给你一个网址，能转能点 |
| **S1** 零件级装配 | 装配树 + 拆解 + 爆炸 + 逐零件导出 | Blender 里能单独打开任一颗零件并编辑 |
| **S2** 风洞视觉层 | L1 粒子/流线/压力云图 + 滑杆 + 烟线视频 | 拖滑杆能看见流场变化 |
| **S3** 风洞计算层 | RapidFOAM 在 CI 上跑真算，结果回填 | 拿到 Cd/Cl 与流线图 |
| **S4** 驾驶模式 | 赛道 + 物理 + HUD + 悬架联动 | 能用键盘把车开起来 |
| **S5** 精修 | 精确车架/悬架几何、材质渲染、答辩素材、封装成你的 Codex 技能 | 可直接用于汇报 |

S0 有两种走法：GitHub 授权到位 → 直接 CI + Pages 上线；暂时没有 → 我在本机把骨架和网站搭好，离线就能打开，等你给授权后一次性推上去。

## 6. 需要你提供

1. **有没有现成 CAD**（STEP / SolidWorks 装配）？决定走路线 A 还是 B。
2. **车的基本数据**：轴距、轮距、轮径、整车质量、前后质量分配、动力形式（油 / 电）。
3. **GitHub 通道**：装 `gh` 你登录 / 给我 PAT / 你先建空仓给我地址。
4. 风洞你要的是**能讲清楚的可视化**，还是**要拿去写进报告的数值**？前者投入小得多。
5. 要不要在本机装 BlenderMCP 作为实时编辑加速器（需装 Blender + uv，见 PLAN.md 附录 A）。

## 7. 代价与风险（实话）

- 浏览器四模式本身不难，**主体工作量在几何与数据管线**，不在网页。
- 真 CFD 每次 1–4 小时 CI 机时；公开仓库免费，私仓会吃额度。
- 驾驶物理是游戏级，不要当圈速工具用。
- 几何精度上限由你提供的真实数据决定；给不了真实尺寸，那就是"比例正确、尺寸待校准"的模型。
- 我无法替你注册 GitHub 账号，也不会在无授权情况下推送代码。

**结论：只要仓库设为 public，从建模、Blender 组装、CFD 求解到网站发布，全程零花费。** 唯一"花费"是机时占用与等待时间。

### B.2 机时：每次风洞计算的实测档位

RapidFOAM 自带三档网格预设（约 3 米模型，官方标注为粗略估计，未经基准测试）：

| 档位 | 基础网格 | 表面/边细化 | 边界层 | y+ 目标 | 目标单元数 | **预计时长** |
| --- | --- | --- | --- | --- | --- | --- |
| `fast` | 0.15 m | [3,4] / 5 | 5 | ~50（壁面函数） | ~3–5 M | **10–20 分钟** |
| `standard` | 0.10 m | [4,5] / 6 | 8 | ~30（壁面函数） | ~9–13 M | **1–2 小时** |
| `fine` | 0.08 m | [4,5] / 7 | 20 | ~1（解析到壁面） | ~20–28 M | **4–6 小时** |

**针对"讲得清楚的可视化"这个目标：用 `fast` 档就够。** 一次 10–20 分钟、公开仓库免费，可以跑十几二十次做对比（改尾翼、改攻角、不同偏航角），而不会产生任何费用。

### B.3 真正的成本：几何，不是渲染

| 环节 | 成本量级 |
| --- | --- |
| 网站四模式（three.js 页面） | 小。库都成熟，主要是组装与调试 |
| Blender 无头组装 + 逐零件导出 | 小到中。脚本一次性写好，之后全自动 |
| 风洞可视化（流线 / 压力云图 / 粒子） | 中。vtk.js 承担主要渲染工作 |
| 驾驶模式 | 中。赛道生成 + 物理参数调校 |
| **几何本体（车架 / 悬架 / 车身）** | **大，且是唯一真正的瓶颈** |

几何的代价完全取决于你们手上有什么：

- **有 STEP 装配** → 我写导入转换脚本按零件拆解并保留名称，几天量级。
- **从零参数化建** → 每个部件的尺寸都要定，需要多轮迭代与你的确认，是周量级，且精度受限于你给的数据。

### B.4 你的时间成本

几乎全部集中在前置输入：轴距、轮距、轮径、整车质量、前后配重、动力形式、有没有现成 CAD。给齐之后主要是我在跑，你只需要在每个阶段的验收点看一眼、说行或不行。

### B.5 省钱省时的建议顺序

1. 先做 S0 + S1（整机 + 拆解），**不碰 CFD**——这一步就能交付一个"能转能拆"的网站给你。
2. 风洞先用 `fast` 档跑一两次拿真实数据，喂给可视化层；不满意再升档。
3. 驾驶模式放最后，因为它是锦上添花，不构成"讲清楚"的必要条件。
